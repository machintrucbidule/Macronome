# ADR-0003 — Installable PWA (app-shell service worker, no offline data)

Status: **Accepted**.
Date: 2026-06-11.

> This ADR records the decision to ship Macronome as an installable Progressive Web App.
> It builds on ADR-0001 (the API serves the SPA): the PWA assets are plain static files,
> so the deployment shape is unchanged. A new session must not reintroduce offline-data
> caching or a separate web host.

---

## Context

After the mobile-responsive milestone the SPA is usable on phones, but it still runs as a
browser tab: no home-screen install, no app icon, no standalone chrome, and updates depend
on a manual browser refresh. The owner wants a real installable app (BACKLOG PWA-1) — an
icon on the home screen, a standalone window (no URL bar), and a self-updating shell —
**without** an offline-data mode (the tracker is intentionally network-required: every
nutrition figure is computed server-side, CLAUDE.md rule 2).

## Decision

1. **Installable PWA via `vite-plugin-pwa` (Workbox).** The web build emits a
   `manifest.webmanifest` (`display: standalone`, `start_url: '/'`, theme/background
   colours, app icons) and a service worker that **precaches the built app shell only**
   (HTML/JS/CSS/icons). These are ordinary files in `packages/web/dist`, served verbatim
   by the existing `serveSpa` (`packages/api/src/http/spa.ts`) — **no deployment change**,
   no conflict with ADR-0001.
2. **App-shell cache only — no offline data.** There is **no runtime caching of `/api`**;
   the service worker's navigation fallback explicitly denies `/api/*`
   (`navigateFallbackDenylist`), mirroring `serveSpa`'s own `/api` exclusion. The network
   is still required for all data. Offline-data mode is **out of scope** (owner decision).
3. **Silent background updates, applied on next launch.** A new build installs its service
   worker in the background; it activates on the **next app launch** — **no in-session
   prompt and no surprise reload**. A manual **"Forcer la mise à jour"** button in
   Paramètres forces immediate activation + reload for users who want the update now.
4. **Standalone theming.** A dynamic `theme-color` meta tracks the live `--bg` token so the
   OS status bar follows the in-app theme; apple meta tags + an apple-touch icon give iOS a
   home-screen entry (iOS installs via Safari's Share → Add to Home Screen).
5. **Native touches (scoped).** An Android/Chromium **install invite** (`beforeinstallprompt`)
   and light **haptic feedback** on key successes. iOS exposes neither API; nothing is shown
   there (no iOS-specific hint). Web Share and barcode scanning are out of scope.

## Consequences

- The build gains `vite-plugin-pwa`; icons are pre-generated once
  (`@vite-pwa/assets-generator`, a manual `gen:icons` step) and committed under
  `packages/web/public`, so neither CI nor the Docker build needs `sharp`.
- No API, schema, or migration change. The only server surface touched is the already-public
  `GET /api/v1/health`, now read by the SPA to display the running version on the update card
  (this lifts the ADR-0002 "web display deferred" note — see ADR-0002 + DECISIONS PWA-1).
- The service worker is inert in dev (Vite serves the SPA); it is built and registered only
  from the production bundle the API serves.
